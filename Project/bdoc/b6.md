# bmod6-auth  (NEW)

**Purpose:** Account sign-up, login, and route protection using only **Patient ID** and **password**.

## Endpoints
### `POST /api/auth/signup`
```json
{ "patient_id": "PAT-1024", "password": "Str0ngPass1" }
```
- `201` returns `{ "status": "success", "patient_id": "PAT-1024", "access_token": "...", "token_type": "bearer" }`
- `409 PATIENT_ID_TAKEN`, `422 VALIDATION_ERROR`

### `POST /api/auth/login`
Same body. `200` returns the token. Any failure returns `401 INVALID_CREDENTIALS` with the same message for unknown ID and wrong password. Too many failures returns `429 TOO_MANY_ATTEMPTS`.

### `GET /api/auth/me`
Requires `Authorization: Bearer <token>`. Returns `{ "patient_id": "PAT-1024" }`.

## Rules for credentials
- Patient ID: 4 to 20 characters, `A-Z a-z 0-9 - _`; stored normalised to upper case so IDs are unique regardless of case.
- Password: 8 to 64 characters, at least one letter and one number (bcrypt limits input to 72 bytes).
- Passwords stored only as **bcrypt hashes** (via `passlib` or `bcrypt`); never logged or returned.
- Tokens: signed JWT (HS256) with `sub` = Patient ID and a 30-minute expiry; `SECRET_KEY` comes from `.env` and must be long and random.
- Brute-force protection: lock a Patient ID for 15 minutes after 5 failed logins (and rate-limit by IP).

## Data model (SQLite for development, PostgreSQL for production)
| Table | Columns |
| --- | --- |
| `patients` | `patient_id` (PK), `password_hash`, `created_at`, `failed_attempts`, `locked_until` |
| `prediction_history` *(optional)* | `id`, `patient_id`, `created_at`, `risk_category`, `probability`, `input_values` (no raw report files) |

## FastAPI integration
`get_current_patient` dependency decodes the token and is added to `/api/report/upload` and `/api/predict/manual`. `/api/health`, `/api/model/info`, and the auth routes stay public.

## Limitations (state clearly in README and UI)
- No password recovery in v1 because no email or phone is stored.
- Patient ID is chosen by the user; it is a login name, not a hospital record number, and is not verified against any hospital system.
- Use HTTPS in any real deployment.

## Done when
- Passwords never appear in the database, logs, or responses.
- Expired or tampered tokens return 401.
- Duplicate Patient IDs differing only by case are rejected.
